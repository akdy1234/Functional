## Question 1 — Triangle Numbers

**1.1 `triangleNumber`** — *What:* an inner helper `aux n` returns a pair `(sum, listSoFar)`, consing the newest triangle number onto the front each time. *Why cons instead of append:* `prevList @ [curSum]` is O(n) per call (has to walk the whole list to append at the end), which would make the whole thing O(n²); consing is O(1) per call, which is where linear complexity actually comes from — the cost is that the list comes out in **decreasing** order (newest first), so we `List.rev` once at the very end. That's exactly what the exam's hint about `List.rev` is pointing you toward. *Why it's not tail recursive:* the tuple `(curSum, curSum :: prevList)` is built *after* `aux (n-1)` returns — there's work left pending once the call comes back. *How to recognize this pattern:* any time a question demands "recursive but NOT tail-recursive" **and** "at most linear complexity" in the same breath, that combination is the signal to build the answer via cons+reverse rather than via `@`/`List.last`, which is the naive-but-quadratic instinct.

**1.2 `triangleNumberAcc`** — *What:* walk `i` from 1 to `n`, tracking a running `sum` and consing each new value into an accumulator (again in reverse), one `List.rev` at the end. *Why tail recursive:* `aux (i+1) sum' (...)` is the entire result of its branch — nothing pending — so it compiles to a loop. *How to recognize:* "tail-recursive with an accumulator, same behavior as [a non-tail-recursive sibling]" is almost always solved by turning the non-tail version's "wait for the answer then do X" into "carry the partial answer forward and update it as you go."

**1.3 `triangleNumberList`** — *What:* `[for i in 1..n -> List.sum [for j in 1..i -> j]]` — literally two nested comprehensions, no recursion. *Why this is allowed to be O(n²):* the question explicitly raises the complexity ceiling here (only "at most quadratic," vs. linear for 1.1/1.2) precisely because it wants you to lean on `List.sum` (which itself is O(i) per call) rather than build anything clever — this is the "give the simplest possible correct thing" question of the trio.

**1.4 `sequence`** — *What:* a generic tail-recursive accumulator walk, identical shape to 1.2, except the "step" is an arbitrary caller-supplied `f k prev` instead of always `+`. *Why this generalizes 1.1/1.2:* triangle numbers are the special case `f = (+)`, starting value `1` — the question even tells you this directly ("triangleNumber... can be written as `sequence (+) 1`"). *How to recognize when a question wants you to "notice a pattern is a special case of something more general":* whenever an earlier answer's core loop (here, "carry forward and combine") reappears with the *combining operation* as the only thing that changed, that's your cue that the general version just parameterizes over that operation.

**1.5 `alternatingTriangle`** — *What:* built entirely on top of `sequence` with `f k acc = if k is even then acc - k else acc + k`, and initial value `1`. *Why no recursion of its own is needed:* once you have `sequence`, "alternating triangle numbers" is just a different `f`, not a different algorithm — this is the direct payoff of having generalized in 1.4. *How to double check your `f`:* plug in `k=2` by hand — `A2 = A1 - 2 = 1 - 2 = -1`, matching the example `[1; -1]` — confirms the sign convention (subtract on even `k`, add on odd `k`) before trusting the rest.

## Question 2 — Code comprehension

**2.1 (identify + name + two "what if" questions)** — Trace `foo [1;2;3;4]` by hand: it produces `[(1,2); (2,3); (3,4)]` — every *overlapping consecutive pair*. `bar f pairs` walks a list of pairs and requires `f x y` to hold for every one (true on the empty list — vacuous truth, matching the `(*3*)` line). `baz` composes them with `f x y = (x+y) % 2 <> 0` — checking that every consecutive pair sums to an odd number, which happens exactly when the two elements have *different* parity — so `baz` checks whether the list **strictly alternates** between odd and even. Names: `foo → consecutivePairs` (this is literally `List.pairwise`), `bar → forallPairs` (this is `List.forall` specialised to pairs), `baz → alternatesInParity`.

- *`[x]` → `[_]`:* no behavior change — `x` is never used in that branch, so this only removes an "unused variable" compiler warning.
- *Swap `(*1*)`/`(*2*)`:* **does** change behavior, because `_ :: xs -> false` (no guard) would now sit *above* the guarded case and intercepts every non-empty list unconditionally — the guarded rule becomes unreachable. `baz` would collapse to "true only for lists of length ≤ 1, false otherwise," regardless of actual parity.
- *Swap `(*2*)`/`(*3*)`:* **no** change — `_ :: xs` and `[]` never match the same input, so their relative order is irrelevant.

*How to reason about "does swapping match-cases matter":* it only ever matters when the two patterns can **overlap** on some input — check that first before anything else; if they're disjoint (like empty-list vs. non-empty-list), order is free.

**2.2/2.3 `baz2`** — *What:* `xs |> List.pairwise |> List.forall (fun (x,y) -> (x+y)%2 <> 0)`. *Why this is "clean and simple":* `List.pairwise` and `List.forall` are literally the standard-library functions that `foo` and `bar` were reimplementing by hand — the question explicitly permits standard-library functions, so the simplest correct answer is to recognize that and use them directly rather than write any recursion at all. *The two contrasting example lists* (`[1;2;3;4;5;6]` → alternates → `true`; `[1;2;3;4;5;7]` → last two are both odd → `false`) are included as top-level values in the file so you can paste them straight into FSI to double-check.

**2.4 (why `foo` isn't tail recursive)** — Same style of argument as the previous exam's `baz`: hand-trace `foo [1;2;3;4]` and notice every step produces `(x,y) :: (foo ...)` — the cons wraps *around* the recursive call rather than being its entire result, so the evaluator has to keep a growing chain of "still owed" cons operations pending until it reaches the base case. That's the call-stack signature of non-tail-recursion.

**2.5 `fooTail`** — *What:* continuation-passing version — instead of `(x,y) :: (result)` happening *after* the call returns, we pass a continuation `c` that says "here's what's still owed," and the recursive call `aux (y::xs) (fun acc -> c ((x,y)::acc))` becomes the entire result of its branch. *How to recognize when CPS is the fix:* exactly the same signal as before — "make [a function using `::`/`+`/etc. *after* a recursive call] tail recursive using continuations" is CPS's signature use case.

## Question 3 — Stores and locks

**3.1 `newStore`/`lock`/`unlock`** — *What:* straightforward `match st.owner with` on `None`/`Some pid2` (with a guard `pid2 = pid` for the "you're allowed to unlock your own lock" case), printing the exact error strings the spec demands and returning the store **unchanged** whenever an operation fails. *Why returning `st` unchanged on failure matters:* the whole point of a lock is that failed operations must be no-ops — if `lock`/`unlock` silently succeeded on failure, the mutual-exclusion guarantee the rest of Q3 depends on would be broken.

**3.2 `read`/`write`/`isLocked`** — *What:* `read` is just `.data`; `write` checks whether the store is locked by someone *else* (`Some pid2 when pid2 <> pid`) and refuses (printing the error) if so, otherwise updates `data` — note that writing while *unlocked*, or while locked *by yourself*, is always allowed (both fall into the `| _ ->` catch-all). `isLocked` is `Option.isSome`.

**3.3 `inbox` (the mailbox loop)** — This is the hard one, so here's the reasoning in full:
- *What each message does:* `Lock` either grants immediately (store unlocked) or queues `(pid, rc)` into `pending` for later (store already locked). `Unlock` calls your `unlock` function, and — **only if that actually succeeded** in freeing the store — hands the lock straight to the next queued process (if any) and replies on *their* channel, otherwise just continues unlocked. `Read` replies immediately (reads always succeed, regardless of lock state, matching the "all reads succeed" note in the PDF). `Write` just re-runs your `write` function and continues with whatever store it returns (success or the printed-error/unchanged version).
- *Why check `isLocked st'` before touching `pending`:* if some process calls `Unlock` without holding the lock, your `unlock` function already prints its own error and returns the store **unchanged** — meaning it's still locked by whoever actually held it. If we blindly tried to hand the lock to the front of the pending queue at that point, we'd be attempting to grant a lock on a store that's still owned by someone else, which `lock` would then (correctly, but confusingly) refuse with a second, spurious error message. Checking `isLocked st'` first avoids that entirely — we only try to serve the queue when the store is genuinely free.
- *Why this doesn't break the store's abstraction:* the loop only ever calls `lock`/`unlock`/`read`/`write`/`isLocked` — never touches `.data`/`.owner` directly — exactly as required.
- *How to think about the `pending` queue generally:* it's just "who's waiting," and the only two things that can change it are a new `Lock` while busy (append to the back) and an `Unlock` that frees the store (pop from the front and immediately re-grant).

**3.4 `createStore`/`storeLock`/`storeUnlock`/`storeRead`/`storeWrite`** — *What:* thin wrappers around `MailboxProcessor.PostAndReply`/`.Post`. *Why `Lock` and `Read` use `PostAndReply` but `Unlock` and `Write` use `Post`:* the question's own signatures tell you this — `storeLock`/`storeRead` are specified to *wait* for the mailbox's reply (`unit`/`'a` respectively — you need the actual value back, or need to know the lock is genuinely yours before proceeding), while `storeUnlock`/`storeWrite` are specified to "return immediately without waiting for a reply" (fire-and-forget is fine — nobody downstream needs to synchronize on those completing). *How to recognize which to use in general:* if the caller's very next line logically depends on the operation having *already happened* (you can't read/write-after-lock until the lock is confirmed), you need `PostAndReply`; if the caller doesn't need to know when it's done, `Post` is enough and keeps things responsive.

**3.5 `inc`/`countTo`** — *What:* `inc` does lock → read → write(+1) → unlock, in that order, so the whole read-modify-write is protected end to end. `countTo` spawns one `async { inc pid st }` per process id, runs them all via `Async.Parallel |> Async.RunSynchronously` (which blocks until every one has finished), then reads the final value. *Why the result is reliably exactly `size`:* because `storeLock` blocks (via `PostAndReply`) until the mailbox actually grants that process the lock, no two `inc` calls can have their read-modify-write interleaved — the mailbox loop serializes them by construction, so there's no lost-update race condition despite the outer `List.map`/`Async.Parallel` genuinely running them concurrently.

## Question 4 — Tic-tac-toe

**4.1 (types + `newGame`)** — *What:* `row`/`col` as tiny single-case wrapper types (`Row of int`, `Col of int`) so `topRow`/`midRow`/`botRow` and `leftCol`/`midCol`/`rightCol` are distinct, nameable, comparable values; `player = X | O`; and the board itself as `Map<row * col, player>`, where an empty map is exactly an empty board (`newGame = Map.empty`). *Why a `Map` and not, say, a 3×3 array or list-of-lists:* the question explicitly tells you to look ahead at 4.1/4.2 before committing — since every later operation is "is this square occupied, and by whom" (a lookup) or "is this line all the same player" (an existence check over 3 lookups), a sparse map keyed by `(row, col)` makes every one of those a one-liner, with zero index-arithmetic bugs to worry about, and it trivially supports "no tile placed yet" as "key absent" rather than needing a separate `None`/empty-cell case.

**4.2 `doMove`** (⚠️ *see the naming note in the code — the prose says "doNextMove" but every example calls "doMove"; I went with what the examples actually use*) — *What:* pattern-match on `state`; if the game's already finished, hand the state back unchanged (this exact behavior — `Ok(Win(p,b))`/`Ok(Draw b)` pass-through — is spelled out explicitly in the PDF's bullet list, it's not something you have to infer); otherwise check it's the right player's turn, check the target square is empty, place the tile, and check win/full/continue in that order. *Why check win before checking full:* a winning move can also be the 9th/final tile — you want `Win` to take priority over `Draw` in that case, which "check win first" naturally gives you. *How the win-check works:* a fixed list of the 8 possible three-in-a-row lines (3 rows, 3 columns, 2 diagonals), and `isWinFor p b` just asks "does every square in *some* line belong to `p`."

**4.3 (state monad wrapping)** — Structurally identical to the N-Queens exam's `chessMonad` — same reasoning applies: `doMove2`/`gameOver`/`getBoard` are the bridge between the plain `Result<state,error>` world of 4.2 and the monad's `Result<'a*state,error>` shape, which is why (per the question) they're allowed to pattern-match `TTT` directly, while everything built on top of them (4.4) is not. **Worth flagging explicitly:** the PDF's own snippet for `evalTTT` (`let evalTTT (TTT f) l = f (Running(empty, X))`) looks inconsistent with how the function is actually *used* in every example (always called with exactly one argument, e.g. `evalTTT gameOver`) and with the `state` type's own declared argument order (`Running of player * board`, so player should come first, not `(empty, X)`). This smells like either a PDF-extraction glitch or a leftover copy-paste from the very similar N-Queens exam (where the extra parameter, `N`, meaningfully mattered as a board *size* — there's no equivalent for a fixed 3×3 tic-tac-toe board). I implemented `evalTTT` to match actual usage: one argument, `f (Running(X, newGame))`. **Please check your real template stub for this one specifically** and adjust if it disagrees — it's the single most likely spot in this whole file to not match what you'll actually be handed on the day.

**4.4 `playGame`** — *What:* a `ttt { }` computation-expression recursion: on each move, check `gameOver` first — if the game's already finished, stop and return the board (this is exactly why the trailing move in the example, played after a win already occurred, "never gets played"); otherwise play the move and recurse on the rest of the list; and if the move list itself runs out first, likewise just return the board. *Why check `gameOver` on every step rather than once at the start:* the game can end *partway through* the list (as in the example — a win after move 5 leaves move 6 unplayed), so the check has to happen freshly before every remaining move, not just once up front.
