## Question 1 — Parametric Lucas numbers

**1.1 `lucas_number`** — *What:* direct if/elif/else translation of the recurrence `L(0)=0, L(1)=1, L(n) = k*L(n-1)+L(n-2)`. *Why:* the question literally gives you the recurrence; there's nothing to invent, just transcribe it. *How to recognize:* whenever a problem hands you a mathematical recurrence with base cases, your first draft is almost always "copy the cases as guards, non-tail recursive calls for everything else."

**1.2 `lucas_number_acc`** — *What:* a helper `aux n a b` where `(a, b)` are always two *consecutive* Lucas numbers, sliding forward each step (`aux (n-1) b (k*b+a)`), until `n=0` returns `a`. *Why tail recursive:* the recursive call `aux (n-1) b (k*b+a)` is the **entire** result of that branch — nothing wraps around it — so F# compiles it to a loop, giving you linear time and no stack growth. *How to recognize "tail recursive, wants an accumulator":* whenever you see this phrasing, ask "what's the minimum state I need to carry forward instead of computing from scratch?" For a linear recurrence like this, the answer is always "the last two values."

**1.3 `sqrt_approx`** — *What:* plug `L(n)` and `L(n-1)` (via 1.2) into the given formula `2*(L(n)/L(n-1)) - k`. *Why floats:* division must be on `float`s or F# does integer division and truncates. *How:* whenever a formula from the problem sheet has a fraction, cast to `float` before dividing, not after.

**1.4 `approx_steps_needed`** — *What:* compute the real `sqrt(k²+4)` once, then linearly increase `n` from 2 until the approximation is within `epsilon`. *Why start at n=2, not n=0:* `sqrt_approx` internally needs `L(n-1)`, and the question demands `n > 1` anyway. *How:* "smallest n such that <condition>" is almost always a simple `while`/tail-recursive counter that stops on the first hit — no need to search cleverly, exams reward correctness over cleverness here.

**1.5 `lucas_seq`** — *What:* `Seq.unfold` builds a lazy infinite sequence from a seed and a step function `state -> (element, nextState) option`. Our state is the pair of the last two Lucas numbers. *Why this avoids recomputation:* each new term is produced in O(1) from the previous state — nothing is ever recomputed, and `seq` is lazy so nothing is generated until something like `Seq.take` actually asks for it. *How to recognize:* "infinite sequence, avoid recomputing" is the textbook signature of `Seq.unfold` (as opposed to `Seq.initInfinite`, which recomputes from scratch each time, or a naive recursive list, which isn't lazy).

## Question 2 — Code comprehension

**2.1 (identify + name + restrict)** — Trace it by hand on a concrete input (e.g. `bar 12`): `foo 12 2` checks `12 % 2 = 0` → true → returns `2`. So `bar` finds the *smallest divisor ≥ 2*, which is always prime. `baz 12` then repeatedly divides out that smallest prime: `2 :: baz 6`, `2 :: baz 3`, `[3]` → `[2;2;3]` — a prime factorization. **How you'd figure this out on the exam:** pick a small concrete number, hand-evaluate one full call chain, and the pattern ("smallest divisor," "divide it out," "repeat") becomes obvious much faster than staring at the code abstractly.

**2.2 `foo2`** — *What:* drop the `x = a` guard. *Why it's still correct:* when `a` reaches `x`, `x % a` is `x % x = 0`, so the second guard already fires — the first guard was never doing independent work. *How to spot redundant guards generally:* ask "is there any input where guard 1 fires but guard 2 wouldn't have?" If no, guard 1 is dead weight.

**2.3 `baz_inverse`** — *What:* `List.fold (*) 1`. *Why:* `baz` produces a prime factorization, and the defining property of a factorization is that its factors multiply back to the original number — so the inverse is just "multiply them." *Bonus:* this even handles the `x=0` and `x=1` edge cases for free (product of `[0]` is `0`, product of `[1]` is `1`), which is a nice sign you found the *intended* solution rather than a coincidental one.

**2.4 (which function isn't tail recursive, and why)** — **`baz`**. Hand-trace `baz 12` (full trace is in the code comments): every step produces `y :: (baz ...)` where the `::` **wraps around** the recursive call rather than being its entire result. The evaluator has to remember a growing chain of pending `::` operations ("owe a `2::`, owe another `2::`, ...") until it finally reaches the base case and can start applying them from the inside out — that "remember what's still owed" is exactly what a call stack does, and it's precisely what a *tail* call avoids (a tail call's result **is** the function's result, full stop). *How to write this kind of proof on the exam:* pick a concrete call, show the literal evaluation chain step by step (matching their `(5+4)*3 --> 9*3 --> 27` style), then point at the specific step where an operation is left "hanging" around a recursive call.

**2.5 `cont`** — *What:* continuation-passing version of `baz`. Instead of doing `y :: (result)` *after* the recursive call returns, we pass a function `c` meaning "here's what still needs wrapping around the final answer," and grow `c` on each step instead of growing the call stack. The base case finally *invokes* `c` with the accumulated base value. *Why this is tail recursive:* `bazC (x/y) (fun acc -> c (y :: acc))` is now the entire result of its branch — the `y ::` moved *inside* the continuation instead of wrapping the call. *How to recognize when CPS is the fix:* any time you're asked to "tail-recursively do the same thing as [a non-tail-recursive function using ::/+/*after* a recursive call]", CPS is the standard tool — the operation that used to happen "after" the call moves into a closure that happens "before" (i.e., inside the continuation), so the call itself becomes the last thing done.

## Question 3 — The robbers language

**3.1/3.2 `encode`/`decode`** — *What:* walk the character list one (encode) or up-to-three (decode) characters at a time. Encode: consonant → `c,'o',c`; else → `c`. Decode: pattern-match "consonant, `'o'`, same consonant" as one unit that collapses back to a single character; anything else, keep the character and move by one. *Why non-higher-order is easy here:* the problem is inherently "look at one character (or a fixed small window), decide, recurse on the rest" — that's exactly what plain pattern matching on lists does. *How to recognize the decode pattern:* whenever you're undoing a fixed-width encoding, match on a fixed-size prefix of the list (`c :: 'o' :: c2 :: rest`) with a guard, and fall through to a smaller pattern otherwise — F#'s pattern match tries them top to bottom, so put the more specific (3-element) case first.

**3.3 `encode_fun`/`encode2`** — *What:* `encode_fun` is `List.map f` + `String.concat ""` — genuinely just "apply a per-character function and glue results together," which is why it's higher-order (it takes `f` as a parameter). `encode2` reuses it by handing in the specific robbers-language rule as a lambda, with zero recursion of its own. *Why this is "simpler":* Q2.2's spirit applies again — once you have a generic "map + concat" tool, the specific encoding is just data (a function value), not a new algorithm. *How to recognize when to reach for `encode_fun`-style refactor:* if you notice two functions have identical *shape* (walk a collection, transform, concatenate) but different *per-element rule*, that's a sign to factor out the walking/concatenating and pass the rule in as a function argument.

**3.4 `parser_robbers_language`** — *What (conceptually):* consume any character, map it through the same "double if consonant" rule as `encode`, and repeat until input is exhausted, joining the pieces. *Why I've flagged this one:* I don't have access to your actual `JParsec.TextParser` module's exact function names (`anyChar`, `many`, `|>>` are my best guess based on standard parser-combinator naming conventions used in courses like yours, but your library might spell them slightly differently, e.g. `pAny`, `manyChars`, or use `>>=` instead of `|>>`). **Before the exam**, open your project's Parser/JParsec source or lecture slides and confirm: (a) the "consume any single character" primitive, (b) the "repeat zero-or-more times" combinator, and (c) the "map the result of a parser through a function" combinator. Once you have the three real names, drop them into the same three-line shape I used and it'll work — the *logic* (map each char, then repeat, then join) is the part that's exam-safe; only the *names* are uncertain here.

**3.5 `encode_par`** — *What:* split on spaces into a word list, chunk it into (up to) `num` roughly-even pieces via `List.chunkBySize`, spin up a `Task` per chunk that runs the ordinary sequential `encode` (from 3.1) over its words and joins them with spaces, then join the per-task results with spaces. *Why ceiling division for chunk size:* `List.chunkBySize k` groups every `k` consecutive words into one chunk — to get *at most* `num` chunks (one per task) out of `n` words, you need chunk size `⌈n / num⌉`, otherwise you'd end up spawning more tasks than requested. *Why this stays "functional":* we never mutate anything — `.Split` just reads the string, everything downstream is ordinary immutable lists and the reduce-style multi-task pattern reads as data flowing through pure transformations, with the *only* side-effecting piece being `Task.Run` itself (unavoidable, since the question explicitly asks for parallelism).

## Question 4 — The N-Queens problem

**4.1 `board`** — *What:* a record `{ size : int; queens : (int*int) list }`. *Why this representation and not, say, an array or a `Map`:* the question forbids mutable structures for later parts anyway, and a plain list of occupied squares makes every other function in the question a one-liner (`List.exists`, `List.length`) rather than needing index arithmetic. *How to decide a data representation on the exam:* skim ahead to what the *later* sub-questions need before committing — here, `valid_solution` just needs a count and `has_queen`/`place_queen` just need membership/conflict checks, so "list of occupied squares" is the least-effort structure that supports all of them.

**4.2 `place_queen`/`valid_solution`** — *What:* `place_queen` checks bounds → checks the square is empty → checks no existing queen shares its row, column, or diagonal (`|Δrow| = |Δcol|`) → if all pass, returns `Some` board with the queen added, else `None`. `valid_solution` just checks `queens.Length = size`, relying on the stated assumption that every board was built exclusively via `empty`/`place_queen` (so it's *already* guaranteed conflict-free — you only need to check that all N rows got filled). *Why the diagonal check is `abs(Δrow) = abs(Δcol)`:* that's the algebraic definition of "on the same diagonal" — it's true in *both* diagonal directions (`/` and `\`) at once, so you don't need two separate checks.

**4.3 `place_queen2`/`valid_solution2`** — *What:* both simply wrap the pure Q4.2 functions inside `CM`, translating `board option` into `('a * board) option`. *Why this is where you're told to "break the abstraction":* these two functions are the *bridge* between the plain-board world (Q4.2) and the monad world — something has to pattern-match on `CM` to construct these values in the first place; everything built *on top of* them (Q4.4/4.5) never needs to.

**4.4 `create_solution`** — *What:* recursively chains `place_queen2 r c >>>= aux rest`, finishing with `valid_solution2`. *Why `>>>=` and not `>>=`:* `place_queen2` returns `unit` — we don't care about its result, only whether it succeeded (short-circuiting via `bind`'s `None` case if it didn't) — `>>>=` is exactly "do this, discard the result, continue," which is the standard `Map`/imperative-`;`-style sequencing operator for a monad.

**4.5 `create_solution2`** — *What:* the same logic, rewritten with the `chess { }` computation expression: `do!` stands in for `>>>=`, `return!` for handing back an already-built `chessMonad` unchanged. *Why it's not allowed to pattern-match `CM`:* the whole point of a computation expression is that the **builder** (given to you, not written by you) is the only place that's allowed to know the monad's internals — your code should read like ordinary imperative-looking steps ("do this, then do that, then return this"), which is exactly what makes computation expressions pleasant to use once they're set up.
